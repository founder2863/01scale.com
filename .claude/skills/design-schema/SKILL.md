# Design a schema

Turns a settled data model into SQL. If the data model is not settled, run `design-data-model` first.

## Read first

`docs/process/DESIGN-RULES.md`, `docs/architecture/DATABASE-DESIGN.md`, the module's data model, and `docs/services/identity/SCHEMA.md` as the example.

## Write

1. **`create table` statements** in the service's own schema, one per table in the data model, in dependency order.
2. **Named constraints** for every rule the database can enforce: primary key, unique, foreign key (inside the schema only), and `check` constraints for formats, lengths, allowed values and ordering of dates.
3. **Indexes**, each with the query it serves. Use partial unique indexes for "only one active" rules.
4. **Grants**: the service's database role can reach only its schema; audit tables are insert and select only.
5. **Sample rows** for each table that satisfy every constraint.
6. **Common queries**: the two or three the service runs most, so the indexes can be judged.
7. A closing list: "Constraints at the schema level".

## Rules that are easy to get wrong

- Names: `<table>_pkey`, `<table>_<column>_key`, `<table>_<column>_fkey`, `<table>_<rule>_check`, `<table>_<columns>_idx`.
- IDs are UUIDv7 generated by the service: no database default.
- `timestamptz` everywhere; every table has `created_at`.
- No foreign key crosses a schema.
- A rule that matters must not live only in application code: if the database can enforce it, it does.
- The SQL is the target that Drizzle migrations must produce. Say so; do not present it as a migration file.

## Checks

- Tables and columns match the data model one for one: same names, same nullability, same limits.
- Every sample row passes every constraint. Read each row against each `check`.
- Every unique rule in the data model has a constraint or index here.
- State plainly whether the SQL has been run against a database. If not, say "not run".

## Output

The SQL, sample rows and queries in `scripts/site/<service>_design.py`; `SCHEMA.md` is generated from it.
