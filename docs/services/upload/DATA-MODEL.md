# Upload service — data model

> **Version 1 · Files to AWS S3.** Status: in design. Stories: `MVP1-E2-01`, `MVP1-E2-02`, `MVP1-E2-03`, `MVP1-E2-04`, `MVP1-E2-05`.

What the service keeps, how the pieces relate, and what every field means. The SQL is in [`SCHEMA.md`](SCHEMA.md); shared database rules are in [`docs/architecture/DATABASE-DESIGN.md`](../../architecture/DATABASE-DESIGN.md).

## Entities

| Entity | Table | What it is | How it relates |
|---|---|---|---|
| File | `upload.files` | A file a user stored, and what Upload knows about it. | Belongs to one user, by `owner_id` only. Other services refer to it by `file_id`. Its content is one object in the S3 bucket. |
| Stored object | (S3, not the database) | The file's bytes, in a private bucket. | Exactly one per file that is not rejected or deleted, at the file's `s3_key`. |
| Audit event | `upload.audit_events` | A permanent record that something happened to a file. | Refers to the file and the user by ID, with no foreign key, so the record outlives a deleted file. |

## Life of each record

| Record | Life |
|---|---|
| File | Created as `pending_upload` → after the check, `ready` or `rejected` → `deleted` when the user or their account deletion removes it, or `expired` after 30 days. A `pending_upload` file left for 24 hours is deleted by the daily clean-up. A file never returns to an earlier status. |
| Stored object | Arrives when the browser sends it → removed at once if the check rejects it, when the file is deleted, or by the bucket after 30 days. |
| Upload and download links | Never stored. Signed on request and valid for 5 minutes. |

## `upload.files`

One row per file. Created when an upload is requested; it never stores the file's content, only where it is and what Upload knows about it.

| Field | Type | Empty allowed | Default | Constraints | What it means |
|---|---|---|---|---|---|
| `id` | `uuid` | No |  | Primary key. UUIDv7, generated by the service | The file's ID everywhere in 01scale. Other services store it as `file_id`. |
| `owner_id` | `uuid` | No |  |  | The user who owns the file: the `sub` of the caller's access token, or `owner_id` sent by an app's server. A plain ID: Identity's tables are not reachable from here. |
| `s3_key` | `text` | No |  | Unique. Always `users/{owner_id}/{id}/original.{ext}` | Where the object lives in the bucket. Built from IDs only, so a file name can never change the path. |
| `file_name` | `text` | No |  | 1 to 255 characters, no `/`, `\` or control characters | The name the person gave the file, shown in the UI and used for downloads. 255 is the longest file name most file systems allow. |
| `mime` | `text` | No |  | One of `application/pdf`, `image/png`, `image/jpeg`, `application/json`, `text/csv` | The file's type, as declared and then confirmed from its first bytes. |
| `size_bytes` | `bigint` | No |  | 1 to 10,485,760 | The declared size, which the upload link enforces. 10 MB keeps a single extraction within the time limits of a serverless function. |
| `pages` | `integer` | Yes |  | 1 to 10 for a PDF; 1 for an image; empty for JSON and CSV | Set when the upload is checked. Empty until then. |
| `accept` | `jsonb` | No | '{}' | Only the keys `mimes`, `max_bytes`, `max_pages` | The calling app's limits at the time of upload, kept so the check on completion applies the same rules. |
| `status` | `text` | No | 'pending_upload' | One of `pending_upload`, `ready`, `rejected`, `deleted`, `expired` | Where the file is in its life (see below). |
| `rejection_reason` | `text` | Yes |  | One of `type_mismatch`, `too_many_pages`, `unreadable`, `size_mismatch`; set exactly when status is `rejected` | Why the check failed, for a plain-language message. |
| `sha256` | `text` | Yes |  | 64 lower-case hex characters; set exactly when the file has been `ready` | A fingerprint of the content, to prove later that the file was not changed and to spot the same file uploaded twice. |
| `created_at` | `timestamptz` | No | now() |  | When the upload was requested. |
| `completed_at` | `timestamptz` | Yes |  | Not earlier than `created_at` | When the check ran. |
| `deleted_at` | `timestamptz` | Yes |  | Set exactly when status is `deleted` | When the file was deleted. |
| `expires_at` | `timestamptz` | No |  | 30 days after `created_at` | When the bucket's lifecycle rule removes the object. Shown to the person so it is not a surprise. |

## Other tables in this schema

The service template also gives Upload `audit_events`, `idempotency_keys` and `outbound_events`. Upload writes `file.created`, `file.uploaded`, `file.rejected`, `file.downloaded` and `file.deleted` to `audit_events`, uses `idempotency_keys` for `POST /files`, and records each processed event's ID so a repeated event has no effect. In version 1 it announces no events of its own.

## Business rules

- A file is usable (can be downloaded or extracted) only when its status is `ready`.
- A file is `ready` only after its stored size matches the declared size and its first bytes match its type.
- A rejected file has no stored object: it is deleted in the same step that rejects it.
- The storage key is built from IDs only, never from the file name.
- One file belongs to exactly one user and is never shared or moved to another.
- Deleting a user's account deletes all their objects and marks all their files `deleted`. Rows are kept, without content, so audit records still make sense.
- A status only moves forward: `pending_upload` → `ready` or `rejected` → `deleted` or `expired`.
- Every change of status writes an audit event in the same transaction.

## What is deliberately not stored

- The file's content: it lives only in S3, never in the database.
- Upload and download links: signed on request, valid for 5 minutes.
- The original path on the person's device: only the file name.
- Anything read from inside the file except its page count: what a document says is Extraction's job, not Upload's.
