# Architecture review: MVP1 design, end to end

> 17 November 2026 · Skill: `review-architecture` · Scope: every MVP1 design before any code is written.

## Scope and method

**Reviewed:**
- the designs of all 9 MVP1 modules:
  - Login and Account management (Identity), Upload, LLM Extraction, Human Review, Payment, Delivery;
  - the DocFlow app;
  - the service template and the gateway;
- `ARCHITECTURE.md` (§12 and its sequence diagram), `API-DESIGN.md` and `DATABASE-DESIGN.md`;
- the stories in `docs/epics/MVP1-EPICS.md`.

**Method:**
1. The mechanical checks in `python3 scripts/site/review_architecture.py`:
   - every call one design makes to another service's endpoint;
   - every event named;
   - every error code by status;
   - every table and its owner column.
2. A manual walk of each multi-service step. For each step I asked:
   - who calls with which credential;
   - what happens if the second call fails;
   - what happens if an event arrives twice, late or out of order.

**Not reviewed:**
- the evals (`docs/evals/EVALS.md`), covered by their own story;
- the MVP2 designs, which don't exist yet.

Both blockers come from one gap: **the design says who a person is, but not who a service is.** Fix that one thing in Identity, then the Major findings, before building `MVP1-E0-07`.

## Blockers

### B1 · No way for a service to get a service token
- **Where:** five designs rely on a "service token" or "service role" that nothing issues:
  - Upload `POST /files` (`owner_id`, "only with the `service` role");
  - Payment `POST /orders` (Service; its `app` column comes "from the calling app's service token");
  - Delivery `POST /messages` (Service);
  - Identity `GET /users/{userId}` (scope `identity:users.read`);
  - DocFlow `DOCFLOW_SERVICE_TOKEN`.
- **Why it's a blocker:**
  - Login's `POST /token` exchanges only a session or an API key.
  - The token's claims (`sub`, `scopes`, `is_admin`, `auth`) have no `role` or `app`.
  - So every service-only check has nothing to check against.
- **Proposal:**
  - Add a client-credentials grant to Identity's `POST /token`. Each service and app gets an ID and a secret, which are Vercel environment variables, stored in Identity as hashes.
  - The token it returns has `sub: service:<name>`, `auth: service`, `app: <name>` and the scopes that service is allowed.
  - Add the claims to Login's token table and `requireService(scope)` to the template.
- **Owner:** Identity (Login spec, `MVP1-E1-03`) and the service template (`MVP1-E0-07`).

### B2 · Steps that run with no person present have no user credential
- **Where:**
  - DocFlow's webhook handlers: on `extraction.job.completed`, DocFlow reads Extraction `GET /jobs/{id}/fields` and calls Review `POST /tasks`. Both are "Signed in", and no user token exists at that moment.
  - Extraction's background job "fetches the file through Upload with the owner's own access token". That token lasts 5 minutes, and storing it would be worse.
- **Why it's a blocker:** `MVP1-E0-09` AC2 says DocFlow forwards the user's token, but the most important step of the process, after extraction finishes, happens with no request from the user.
- **Proposal:** a delegated token. A service with a service token asks Identity for a short token for a named user: `POST /token`, with `on_behalf_of: user_id`, in the style of RFC 8693 token exchange.
  - The token carries the user's `sub` and `act: {sub: "service:docflow"}`, and only the scopes the service is allowed.
  - Every service keeps its single ownership rule ("the token's user owns it"), and audit records both the user and the acting service.
  - Upload's special `owner_id` input can then go, since DocFlow stores the outputs with a token for the user.
  - Extraction uses the same grant when its job starts.
  - Allow it only for services named in configuration, and never with scopes for keys, passwords or accounts.
- **Owner:** Identity (with B1), then Extraction, DocFlow and Upload.
- **Decision for Nikhil:** a delegated token (recommended), or every service accepting service tokens plus an `owner_id`. The second spreads one security rule across six services.

## Major

### M1 · The sequence diagram is out of date
- **Where:** `ARCHITECTURE.md` §12.2.
- **Why:** it has no arrows for:
  - DocFlow reading the fields from Extraction;
  - DocFlow storing the outputs through Upload;
  - the download, which checks Payment and then gets an Upload link;
  - Delivery looking up the email at Identity;
  - the failure branches (`job.failed`, `order.expired`);
  - account deletion fanning out through the outbox.

  Reviewers read the diagram first.
- **Proposal:**
  - Redraw it from the DocFlow design's behaviour lists.
  - Add a second diagram for account deletion.
  - Say which calls use a user token, a delegated token or a service token (after B1 and B2).
- **Owner:** ARCHITECTURE.md.

### M2 · Internal calls and the gateway disagree
- **Where:**
  - Gateway: "services accept requests only with the gateway's shared header".
  - ARCHITECTURE.md "How it runs": DocFlow calls the services directly.
  - Template `callService()`: no address rule.
  - The gateway accepts only a cookie or an `sk_01s_` key, never an access token that already exists.
- **Why:** a direct call from DocFlow to Upload would be refused. A call through the gateway with an access token isn't designed.
- **Proposal:**
  - All calls between services go through `01scale.com/api/...`.
  - The gateway passes a valid access token (`Bearer eyJ…`) through unchanged, after checking only the signature and expiry.
  - Update the flowchart to match.
- **Owner:** Gateway, service template, ARCHITECTURE.md.

### M3 · Endpoints don't state their scope
- **Where:** every service spec. API keys have scopes (`upload:write`, …), but no endpoint says which scope it needs.
- **Why:** `MVP1-E0-06` AC2 ("limited to the key's scopes") can't be tested, and the MCP tools inherit the gap.
- **Proposal:**
  - Add a **Scope** line to every endpoint, beside Access. The rule: `<service>:read` for GET and `<service>:write` otherwise; session-only endpoints say so.
  - Make the `design-api-spec` skill require it.
- **Owner:** each service's spec, and the `design-api-spec` skill.

### M4 · DocFlow acts on stale events
- **Where:** DocFlow `POST /webhooks/{service}`.
- **Why:** after Retry, a late `extraction.job.failed` from the old job would mark a document failed while the new job runs. Likewise, `payment.order.expired` for an earlier order would clear the current one.
- **Proposal:**
  - Act on an extraction event only if its `job_id` is the document's `job_id`.
  - Act on a payment event only if its `order_id` is the document's `order_id`.
  - Acknowledge everything else and ignore it.
- **Owner:** DocFlow.

### M5 · Complete review can stop halfway
- **Where:** DocFlow `POST /documents/{id}/complete-review`.
- **Why:** if Upload is down after Review's task was completed, the document stays `needs_review`. A retry then gets Review's `409 task_completed`, and the person is stuck.
- **Proposal:**
  - On retry, treat `task_completed` as already done and continue from building the outputs.
  - Record the step reached in the process record, for example a status `outputs_pending`, or allow `reviewed` with no outputs until they are built.
- **Owner:** DocFlow.

### M6 · Payment and Delivery call the owner `user_id`, and DocFlow doesn't send it
- **Where:**
  - Payment `POST /orders` and Delivery `POST /messages` take `user_id`.
  - Upload uses `owner_id`.
  - DocFlow's checkout behaviour lists the price, reference and addresses, but no user.
- **Why:** this is a contract mismatch between the consumer and the provider.
- **Proposal:**
  - Once B2 is decided, a delegated token makes the field unnecessary: the user comes from the token.
  - Until then, name it `owner_id` everywhere and add it to DocFlow's behaviour.
- **Owner:** Payment and Delivery (provider first), then DocFlow.

## Checked and sound

- **Every call has an endpoint.** 88 cross-service calls each match an endpoint in the provider's design, with the same method and path. None is missing.
- **Account deletion.**
  - Account management sends `identity.user.deleted` through the outbox.
  - All six receivers handle it: Upload, Extraction, Review, Payment, Delivery and DocFlow.
  - Each says what it deletes. Payment anonymizes orders, Review keeps approved eval candidates without the user's ID, and Delivery cancels queued messages.
- **No foreign key crosses a schema.** Every table has one owner. Every user-owned top-level table has `owner_id` (`user_id` in Identity) and an index; child tables reach their owner through a foreign key inside their own schema.
- **Money.**
  - The price is set only by DocFlow's server.
  - Stripe events are verified and applied once (`payment.stripe_events`).
  - Downloads check the order at Payment every time (§12.4, "check at the moment of use").
  - Agents get a `checkout_url` and can't pay.
- **Files.** Every file moves by a presigned URL of at most 5 minutes; document contents are never logged or stored outside S3.
- **Errors.** Every module uses problem+json. Shared codes (`not_authenticated`, `validation_failed`, `dependency_unavailable`, `idempotency_key_reused`) mean the same thing everywhere, except m1.
- **Idempotency.** Every create endpoint takes `Idempotency-Key` or is idempotent by design, and every event receiver has an inbox.
- **Schemas.** All 8 schemas (7 services plus the template) run on PGlite, and all 44 sample rows pass every constraint (`npm run schema:check`).

## Decisions needed

2. **M2:** all calls between services through the gateway (recommended), or direct calls with the gateway check removed from the services.

Once these are decided, each fix is its own small PR on the owning module, providers before consumers: Identity (B1, B2), then the template and gateway (M2, M3, m3), then Upload, Payment, Delivery and Extraction (M6, m1), then DocFlow (M4, M5, m4), then ARCHITECTURE.md (M1).
